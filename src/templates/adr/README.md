# ADR 索引

このプロジェクトを通じて残る設計判断の記録。**作業単位に着手したら、まずここを読むこと。** 置くだけでは読まれない。

覆したくなった判断があれば、該当の ADR を読んでから提案する。根拠を読まずに別案を出すと、同じ議論を繰り返すことになる。

| # | 判断 | 状態 | 日付 |
|---|---|---|---|

## いつ書くか

**後から「なぜこうなっているのか」と問われうる判断をしたとき。**

- 案が2つ以上あり、1つを選んだ
- 覆すと作り直しになる（データの形、置き場所、外部サービスの選択など）
- 人が停止点で決めた設計上の選択

**書かないもの。** 規約どおりに作っただけのもの、案が1つしか無かったもの。何でも書くと、読まれなくなる。

## どこに、どう書くか

- **ファイル名は英語、連番付き。** `NNNN-kebab-case-in-english.md`（例: `0001-store-sessions-in-postgres.md`）
- **中身はこのプロジェクトの言語でよい**
- 書いたら、この索引に1行足す。**ADR は、判断を含む変更と同じ提出に入れる**

```markdown
# ADR 0001: 判断を一文で

- 状態: 承認
- 日付: YYYY-MM-DD
- 作業単位: <作業単位ID>

## 背景
何が問題だったか。

## 決めたこと
何をどうするか。

## 検討した他の案
それぞれを採らなかった理由。**ここが最も価値が高い。** 書かないと、同じ案が
また出てくる。

## 結果
これで何が変わるか。何を諦めたか。
```

### 人の発言を、そのまま引かない

**何を言われたかではなく、何が問題だったかを書く。** 発言にはその場の言い方が含まれる。後から読む人に要るのは提起の中身であって、言い回しではない。

### 覆すときは、書き換えない

新しい ADR を書き、古いほうの状態を「**NNNN が置き換え**」にする。**本文は直さない。** 当時なぜそう決めたかが読めなくなる。
