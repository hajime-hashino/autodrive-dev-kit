# autodrive-dev-kit

**AIに開発を任せて回すための道具一式。** あなたのプロジェクトに置いて使う。

手法そのものの定義は [autodrive-dev-definition](https://github.com/hajimegane/autodrive-dev-definition) にある。この参照実装は、その定義を動くものにしたものである。

## これで何が変わるか

**AIが開発を主導し、人に残るのは意思決定だけになる。**

環境構築も、着手も、記録も、判定もAIが行う。人が呼ばれるのは、**何を作るか**を決めるとき、**見え方**を決めるとき、**順序**を決めるとき、そしてAIには実行できないこと（外部サービスでの権限付与、資格情報の発行）が要るときである。

そのために、任せて壊れないための仕掛けが一緒に置かれる。

| | |
|---|---|
| **止まる仕掛け** | 提出を経ずに既定ブランチへ入らない。本番の資格情報を手元に持たない |
| **残る仕掛け** | どこで止まったか、何を作り直したか、いくら使ったかが自動で記録される |
| **見る仕掛け** | 上の2つが本当に効いているかを `verify` が判定する。宣言ではなく実測 |

**記録は自慢のためではない。** 何度も同じところで止まっているなら、それは仕掛けにできる。判断がそこにある。

## 使うのに要るもの

読み手として想定しているのは、**Repo や実行環境を自分で用意できる人**である。

| | 何に使うか | 要否 |
|---|---|---|
| Node 22.18 以上 | 道具の実行 | 必須 |
| 作業単位を管理する場所（Linear） | 起票、状態、記録の紐づけ | 必須 |
| Repo（GitHub） | 提出を経て統合する。判定がここを読む | 必須 |
| 動くものを見せる場所（Cloudflare Workers） | 画面の見え方を決めてもらう | 画面があるなら |

## はじめる

```sh
export PATH="$PATH:<この参照実装の置き場所>/bin"

cd <あなたのプロジェクト>
autodrive-dev-kit init
```

いくつか聞かれる。**選択肢と推奨が出るので、番号を選ぶか、そのまま Enter を押す。** 答えた内容は `autodrive.json` に残り、以後は聞かれない。

| 打つもの | いつ |
|---|---|
| `init` | **新しく始めるとき。** 構成を聞いて、土台を置く |
| `apply` | **既にあるプロジェクトへ入れるとき。** 何が置かれているかを見て推測し、確かめる |
| `update` | **道具を新しい版へ入れ替えるとき。** 構成は聞かない。決めた内容は触らない |

置かれた `.env.example` を写して `.env` を作り、資格情報を書く。**人が打つのはここまで。**

## そのあと

Claude Code を開いて、**「はじめる」と伝えるだけでよい。**

```
はじめる
```

コマンドを覚える必要は無い。AIが状態を見て、どこから始めるかを決める。

| | AIが行うこと | 人が行うこと |
|---|---|---|
| 1 | 何を作るか・なぜ作るかを聞き、文書に起こして読み上げる | 話す |
| 2 | 画面があるなら、見え方の案を出す | **選ぶ** |
| 3 | 作る順序の材料を出す | **決める** |
| 4 | 環境を揃える。AIに実行できないものだけ頼む | 資格情報の発行など |
| 5 | 作業単位を起票し、作る | |

**環境は最初に全部揃えない。** まだ要るか分からないものの資格情報を発行させることになるためである。機能ごとに、そのとき必要なものが増える。

**確定度のラベルもAIが付ける。** 「まだ決めていない」「たぶんこう」を聞き取って訳すのはAI側の仕事であり、人が文書の書き方を知っている必要は無い。

見え方の決め方は [docs/design.md](docs/design.md) にある。**画面のあるものを作るなら、ここは飛ばさないこと。**

## 何が置かれるか

| 置かれるもの | 誰のものか |
|---|---|
| `autodrive/` | **参照実装のもの。** `update` で丸ごと入れ替わる |
| `.env.example` / `.github/workflows/verify.yml` / `docs/autodrive.md` | 同上。直したくなったら、こちらへ起票する |
| `autodrive.json` | **あなたのもの。** 構成。入れ替えで触らない |
| `boundaries.yaml` / `docs/what-why.md` / `CLAUDE.md` / `.gitignore` | 同上。既にあれば触らない |
| `.claude/settings.json` | 記録の仕掛けを**足す**。既にある登録は壊さない |

**道具はプロジェクトの中に複製される。** 参照実装を更新しても、`update` を打つまでは変わらない。プロジェクトごとに違う版で動ける（[ADR 0004](docs/adr/0004-vendored-kit.md)）。

テスト、ADR、境界変更の履歴は**生成しない。** そのプロジェクトのものであり、雛形を置くと中身が無いまま残る。

## `verify`

置かれた仕掛けが本当に効いているかを判定する。CI から自動で走る。手で打つこともできる。

```sh
autodrive/verify --root . --scope self
```

定義§9の不変条件それぞれについて、**発効しているか、未発効なら何が手で代替しているか**を出す。

```
[発効]             テレメトリが記録されること
[未発効・代替あり] AIがこれらを無効化できないこと
```

**未発効であること自体は失敗ではない。** 失敗なのは、代替の記録が無いことと、判定ができないことである（定義§9「発効の判定ができない状態は、それ自体を失敗として扱う」）。

判定の中身、境界の進め方、代替の記録の仕方は [docs/verify-criteria.md](docs/verify-criteria.md) と [docs/commands.md](docs/commands.md) にある。

## この参照実装そのものを直す

```sh
npm test    # node:test。テストフレームワークの依存は無い
```

TypeScript を Node で直接実行する。ビルド手順は無い。

**`dependencies` を置かないこと。** 依存ゼロであることが、この参照実装のサプライチェーン上の防御である。追加したくなった場合は [ADR 0001](docs/adr/0001-implementation-language.md) を読み、必要なら更新の提案から始める。

**確認の仕掛けを作ったら、その場で検証する。** テストが書けるものは書く。書けないものは動かしてから提出する。**壊した実装に対してテストが落ちることまで確かめる**（通ることの確認だけでは、何も見ていないテストを見分けられない）。
