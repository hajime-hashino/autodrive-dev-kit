# 記録の仕組み

記録は**外側ループの唯一の入力**である（定義§6）。人やAIが覚えていないと残らない形だと、そもそも改善の材料が集まらない。

したがって、**書き込みは自動で、置き場所は決まっている。**

## 置き場所

```
<対象リポジトリ>/telemetry/<作業単位ID>.jsonl
```

作業単位ごとにファイルを分けるのは、並行作業時の追記衝突を避けるため。索引はディレクトリそのものとし、別に持たない。

## 作業単位マーカー

使用量を作業単位へ紐づけるため、利用側のリポジトリ直下に置く。**追跡対象外**（作業状態であって成果物ではない）。

```
.autodrive/current-work-item.json   {"work_item_id": "AUT-10", "repo": "agent-playground"}
.autodrive/cursors/<セッションID>.json
```

`bin/begin` が着手時に置く。手で書く必要はない。

## トークン消費

実行基盤のフックから呼ばれ、セッション記録から使用量を読んで追記する。

```sh
./hooks/record-tokens   # フックの入力を標準入力から受け取る
```

**フックの登録は利用側のリポジトリの `.claude/settings.json` に置く。** 参照実装側ではない。`verify` が読める場所に置くことで、**外されたときに検出できる**。

設計と、他の経路を採らなかった理由は [ADR 0002](adr/0002-token-usage-capture.md) にある。

## 作業単位に紐づかないやり取り

作業単位を起こすかどうかの検討や、起票される前の依頼は、**どの作業単位にも属さない。** それでも記録は発生する。

これらは `telemetry/unattributed.jsonl` へ**理由とともに残す**。捨てない。

定義§6（v0.10）は、これらを**§6のイベントではない**と整理している。例外ではなく対象外である。したがって作業単位IDを求めない。

**ただし件数は読める形にしてある。** `verify` が観測として出す。

```
観測  作業単位に帰属できなかった記録が 1 件ある
観測  帰属できなかった理由: 作業単位マーカーが無い。作業単位に紐づかないやり取りである可能性がある
```

**量が無視できなくなれば、そこで判断をやり直せる。** 起票を強制する仕掛けを設けないのは、そこを厳密にする労力を他へ向けたほうが効くという判断による（定義§6）。

### 理由を見分ける

解決できない理由は3つあり、**同じ言葉で報告しない。**

| 状態 | 意味 |
|---|---|
| マーカーが無い | 紐づかないやり取りかもしれない。**正常な場合を含む** |
| マーカーが読めない | 壊れている。**紐づけられたはずの記録が帰属しないまま残る** |
| 内容が欠けている | 同上。どの属性が欠けたかも出す |

件数だけでは、紐づく先が無いのか仕掛けが壊れているのかを区別できない。
