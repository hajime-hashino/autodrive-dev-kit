構築例

autodrive-dev-kit を入れたときの構成と、1件の変更が流れる経路です。 各要素はポートとして差し替えられます。ここに出ているのは既定の構成です。

実線 ＝ 操作の流れ 破線 ＝ フィードバック 赤 ＝ 不可逆な操作

2つのループ

内側ループは、実装 → 検証が判定 → 修正を、AIだけで回します。人は呼ばれません。 外側ループは、溜まった記録を読んで仕組みそのものを直します。 boundaries.yaml のセルを動かす変更と、新しい検出手段の導入は外側ループにあたり、 人の承認が要ります。

一般的な構築例との違い

同じ形の図をよく見かけますが、この道具の実物は次の点が違います。 どれも「外に出さない」「既定では持たない」方向のずれです。

左が一般的な構築例、右がこの道具の実物
要素よくある構成autodrive-dev-kit
サンドボックス ローカル、または任意の隔離環境 devcontainer。出口は許可制で、許可する宛先は構成から作られる。起動のたびに適用するため、コンテナを止めても戻らない
Telemetry OTLP Collector で外部へ送る リポジトリの中の telemetry/<作業単位ID>.jsonl。外部サービスへ送らない。記録フックが自動で追記する
記録を読む側 Grafana / SigNoz のダッシュボード invariants（判定器）。ダッシュボードを持たず、不変条件が有効かどうかの判定を返す
Flag 露出制御と即時ロールバック 見せる範囲を段階的に広げる。広げるほうが不可逆で、戻すのは可逆。既定では持たない
Preview 常設の検証環境 既定では持たない。画面を持つ場合に Cloudflare Workers を選べる

本番環境が固定条件であることは同じ

本番データの破壊的操作、金銭の移動、外部への不可逆な公開は固定条件です。 実績が積まれても緩めません。委譲範囲の表を動かして広げられるのは、この外側だけです。
